# The cascade

Written 2026-09-05, round 1. The law every kitchenUI stylesheet follows. Decisions 4 and
5 in `decisions.md`; the survey behind them in `survey.md`. It grows by round: round 2
adds type, space, radius and elevation; component rounds append rulings the day they are
said.

## 1. Layer order

One declaration, the first line of `src/styles/index.css`:

```css
@layer tokens, base, components;
```

- `tokens`: okchroma's emitted CSS and its semantic aliases; later, the CSS generated from
  kitchenUI's own token source.
- `base`: the page rules Base UI's quick start asks for (`.root { isolation: isolate }`,
  `body { position: relative }`) and `color-scheme` per mode.
- `components`: one stylesheet per component.
- A consumer overrides by writing unlayered CSS, which wins over every layer. kitchenUI
  never writes unlayered CSS.

## 2. The mount

- okchroma's CSS is generated at build time by `scripts/emit-tokens.ts` from
  `resolveTheme`, `brandCss` and `signalsCss`, plus okchroma's shipped
  `tokens/semantic.css`, into `src/styles/tokens.css`. The file is generated, marked as
  such, and committed. okchroma is a build-time dependency, never a runtime one.
- The emit declares every token twice: under `[data-brand="kitchen"]` for light and
  under `[data-brand="kitchen"][data-theme="dark"]` for dark, with the brand-independent
  block at `:root`.
- The consumer sets `data-brand="kitchen"` on the element the theme applies to, normally
  `<html>`, and `data-theme="dark"` on the same element for dark mode. kitchenUI sets
  neither; the app does.
- No color value is written anywhere except in the generated file.

## 3. Selector grammar

- One attribute names a part: `data-part`. Its value is the component name on the root
  and `component-part` on inner parts, kebab case, using Base UI's own part names where
  one exists (`menu-trigger`, `menu-popup`) and ours where it does not (`button-icon`).
- Each variant axis is one attribute named for the axis (`data-variant`, `data-size`);
  values are words. Axes are decided in the component's own round.
- State is selected only by Base UI's state attributes (`data-open`, `data-disabled`,
  `data-checked`, `data-pressed`, `data-highlighted`, ...) and the platform's
  pseudo-classes (`:hover`, `:focus-visible`, `:active`). No state classes.
- kitchenUI sets no class on any element. `className` passes through untouched for the
  consumer.

## 4. Color law

okchroma's consumer rules (its `docs/agents.md`) as they apply to a stylesheet. The
roster check holds rules 1 to 3 and 6; rules 4 and 5 are read.

1. Every color in component CSS is `var(--name)` where `--name` is declared in
   `tokens.css`. No hex, `rgb()`, `hsl()`, `oklch()`, `color()`, or named color.
   `currentColor` and `transparent` are the only keywords allowed. A stylesheet may also
   read the variables Base UI sets inline on its own parts (`--anchor-width`,
   `--available-height`, `--transform-origin`, a panel's height, the active tab's box);
   they carry lengths and origins, never colors, and the checker knows their names.
2. One token serves both modes. Component CSS contains no `[data-theme]` selector and no
   `prefers-color-scheme` query; the mode is the emit's business.
3. No intermediate values: no `color-mix()`, no relative color syntax, no opacity on a
   stop. Disabled is `opacity: var(--disabled-opacity)` on the component.
4. Instruments do their jobs: text reads `pencil` or `pen` stops, or `stamp-on` over a
   CTA fill; focus rings, icons and required borders read `highlighter`; interactive
   backgrounds and decorative borders read `chalk`; CTA fills read `stamp-fill` and
   its states, with `stamp-edge` always rendered; elevation reads
   `--surface-dim/low/mid/high`; page grounds read `paper`. Contrast is okchroma's
   guarantee per stop; kitchenUI runs no contrast check of its own.
5. States move along the scale in the order the names imply: rest, hover, pressed.
6. No alias of a roster stop. A stylesheet reads the stop itself, never a name that
   restates it in both modes (`--fg-default` for `--neutral-pen-70`, `--brand-bg-emphasis`
   for `--brand-stamp-fill`). The non-roster names it may read are okchroma's system
   tokens, which carry what no stop does: `--surface-dim/low/mid/high` name a different
   paper per mode, `--scrim` and the alphas name no stop, `--disabled-opacity` is not a
   color. The link trio is on the roster and is read as such, whatever it aliases
   (section 6, decision 17).

## 5. File shape

```
src/
  index.ts                 package entry (JS only)
  styles/
    index.css              the @layer order, then imports in that order
    tokens.css             GENERATED by scripts/emit-tokens.ts
    base.css
  components/<name>/
    <name>.tsx
    <name>.css             imported by styles/index.css, never by the .tsx
    <name>.md              the component's record: parts, states, the token each state
                           reads (shape fixed at round 3)
  tokens/
    brand.json             the seed and the slug; round 2 adds the authored token source
```

- Components never import CSS. The entry stylesheet imports every component stylesheet
  in order, so the package ships one stylesheet.
- Package exports: `.` for the JS, `./styles` for the built stylesheet. A consumer
  imports both.

## 6. No semantic layer

kitchenUI creates no aliases above okchroma's roster (decision 17, closing 3 and 5).
okchroma's premise is that each token promises something; an alias would restate the
promise under a second name, and a designer would then meet two vocabularies for one
color. So a stylesheet reads the stop, and in Figma every property binds to the okchroma
variable the component's record names. okchroma's shipped `semantic.css` still arrives in
`tokens.css` because the emit concatenates it; of its names only the system tokens are
read (rule 6). Its other aliases (`--fg-*`, `--border-*`, `--brand-fg/bg/border-*`, the
signal sets) are declared and unread, and the checker keeps them so.

## 7. Authored tokens

Any token kitchenUI authors itself lives in one source file that is not CSS; the CSS in
the `tokens` layer is generated from it. The format is chosen at round 2 with the first
such token (decision 5).
